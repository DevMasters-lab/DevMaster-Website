Purpose
Translate the accepted agency architecture into a reviewable relational design for PostgreSQL and Prisma, preserving the distinction between an expert accepting an offer and DevMasters selecting that expert.
Scope boundary
Two secure portals: Admin and approved Expert. Companies submit public forms without an account. Experts work directly with the requesting company. No company portal, project tasks, timesheets or deliverable-management entities are included. [S1 §§1–3]

07  Integrity: what must be enforced
The complete register contains 30 specifications (C01–C30). These high-risk rules must be enforced in the database and/or serialized transactions, not just by form validation.
PostgreSQL CHECK constraints cannot validate another table’s state. Composite FKs enforce identity consistency; acceptance/selection-state checks require guarded transactions or triggers. Triggers and unsupported database features belong in reviewed migrations. [T1–T3]

How to read this package
This Word guide explains the model and implementation rules. The accompanying Excel workbook and Markdown specification contain all 442 column definitions, all 80 foreign-key relationships and the full constraint register. This is a design deliverable, not an executed migration or an inventory of an inspected live database.
Convention | Proposed specification
Naming | Plural snake_case tables; stable UUID identifiers supplied by the application.
Keys | PK = primary key; FK = foreign key; UQ = single-column unique. Junctions use a two-column composite PK.
Calendar dates and timestamps | date for calendar dates; timestamptz(3) for events; UTC at application/API boundaries.
Money and capacities | numeric(18,2) for offer compensation. No floating-point money, invoice or payment ledger is introduced.
Draft requiredness | A nullable draft field can become mandatory before issue; required-on-issue rules are not optional business checks.
Concurrency | record_version is a mutable aggregate counter; offer_versions.version_no identifies a distinct terms revision.
Common metadata | created_at is server-generated. Every write path must maintain updated_at and record_version where present.
Foreign-key actions | RESTRICT on delete/update by default. Disable/archive referenced masters instead of cascading away evidence.
JSONB | Only validated snapshots, event data, settings, templates and report filters; use typed FKs for actual relationships.
Technology mapping | Explicit Prisma native types. Verify installed versions before applying migration syntax or special constraints. [T2–T3]

Relationship | Business meaning
Request + expert -> candidate | One shortlist entry per request/expert pair. Multiple role-specific offers may follow from it.
Offer -> versions -> responses | Issued terms and attachments are fixed. A revised offer requires a fresh response to its exact version.
Acceptance -> selection | Acceptance is the expert’s agreement. Selection is a distinct authorized DevMasters decision.
Selection -> placement | A placement points to the same offer, accepted version, acceptance response and SELECTED decision.

IDs | Area | Required invariant
C03 | Same company/contact | A request contact must belong to the linked organization.
C04–C06 | Same shortlist, role and version | Offer candidate matches request/expert; role matches request; current version belongs to offer.
C07–C14 | Exact acceptance-to-placement chain | Decision and placement reference the same offer/version/response. An ACCEPTED response and SELECTED decision must be verified, not merely an existing ID.
C15–C18 | No duplicate business outcome | One candidate per request/expert, scoped revision numbers, one substantive response per version and one SELECTED event per offer.
C19–C23 | Reference and delivery uniqueness | At most one primary company contact, primary CV and active template version; deduplicate inbox entries and delivery attempt sequences separately.
C24–C25 | Valid values and issue readiness | Positive headcounts/sequences; nonnegative compensation; valid date order; complete terms/payer/currency/rate basis/expiry and clean attachments before issue.
C26 | Required first version | Create parent + first version in one transaction; validate parent minimum-child cardinality before commit.
C28 | Availability conflicts | Use an exclusion constraint or a serialized expert-lock transaction to prevent overlapping intervals; extension availability is not assumed.
C29–C30 | History preservation | No new revision after a placement exists. Reject mutation of issued term fields/attachments and rewriting/deletion of acceptance or selection history.
Command | Validate and lock | Write atomically
Submit request | Validate public form and scoped idempotency key. | Request + original snapshot + document ownership links + acknowledgement outbox.
Approve / activate expert | Authorized reviewer; review current application snapshot and required evidence. | Review record + profile state; then account invitation/linking. Portal access still requires all activation guards.
Issue offer | Lock offer; compare record_version; validate current draft, complete terms, future expiry and CLEAN files. | Issued snapshot/hash + current offer state + inbox + audit + outbox.
Revise terms | Lock offer; reject any offer with placement history. | Supersede old current version; create sequential draft; move current pointer. Fresh issue and acceptance required.
Accept / decline / request changes | Lock current version; check ownership, channel, ISSUED state and current time before expiry. | Immutable response + attributed evidence links + offer/version state + audit.
Select expert | Lock request, role when present, then offer; verify accepted current version, authorization and remaining headcount. | Selection decision + placement + inbox + audit + outbox.
Correct selection | Lock same aggregates; verify authorized reasoned supersession. | New decision + cancellation of existing placement where required + audit/notifications; preserve prior records.
Expiry and retry boundaries
A valid acceptance is not retroactively cancelled when its old deadline passes. Late phone/email evidence cannot make a new acceptance valid by backdating responded_at. Retried commands replay the original committed result; email retry never duplicates the selection decision.
Area | Proposed enforcement
Expert isolation | Resolve the logged-in user to their profile and follow owned offer/version/response/placement/document links. Knowing a UUID never grants access.
Staff permissions | Separate expert review, offer management, final selection and system administration. Staff-only notes, audit and delivery diagnostics are not exposed to experts.
Public documents | Use scoped intake authorization. Null uploader_user_id does not make a file public; request/expert document links establish ownership.
Issued attachments | Only exact CLEAN document versions are attached. Freeze bytes, checksums and offer-document membership; never substitute the latest CV/file.
Outbox and inbox | Persist event, business decision and inbox in one transaction. Dispatcher and workers use leases, deterministic keys and retryable delivery attempts.
Ambiguous delivery | SENT means provider acceptance, not confirmed inbox delivery. A provider timeout can leave UNKNOWN status and may cause repeat email; do not promise exactly-once external delivery.
Secrets and temporary state | Protected runtime configuration holds provider/JWT/database/storage secrets. Keep verification/OTP/recovery challenges in expiring Redis state. Never store raw secrets in audit/outbox/settings.
Archive and retention | Default FK actions restrict deletion. Disable/archive referenced masters. Purging, consent text and retention periods require an approved policy and a controlled process.
Exports and recovery | Staff exports are private, reauthorized at execution/download and retained per policy. Test database and linked-object restoration together.
